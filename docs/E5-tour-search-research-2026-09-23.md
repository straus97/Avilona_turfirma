**Как читать оценки:** HIGH — прямое официальное подтверждение рассматриваемого факта; MEDIUM — официальное описание без проверки действующего доступа/полноты либо старый документ; LOW — косвенное или историческое свидетельство; UNKNOWN — публичных доказательств недостаточно. ## 1. Executive summary

**Самый практичный первый вариант E5: готовый мультиоператорный модуль, подключённый к собственному учёту обращений и бронирований Avilona. Первым кандидатом для проверки является Tourvisor; переход на его CRM не нужен как архитектурная цель.** Покупка допустима только после подтверждения состава тарифа и успешной проверки передачи данных. Документированный механизм экспорта и webhook существует, но полноценная связь «выбранный тур → авторизованный турист Avilona» ещё не доказана. [Экспорт Tourvisor](https://wiki.tourvisor.ru/).

Прямой бесплатный путь исследован первым. **АЛЕАН официально предоставляет API бесплатно партнёрам с договором.** У Библио-Глобуса есть официальные программные интерфейсы цен и заявок; у TEZ TOUR — официальная, преимущественно историческая документация XML-шлюзов. Но бесплатность доступа, право объединять выдачу и актуальная работоспособность полного российского контура для Avilona не установлены. Это основания для переговоров и ограниченных интеграций, а не готовый бесплатный аналог большого агрегатора. [АЛЕАН](https://www.alean.ru/page/sotrudnichestvo/?label=api), [Библио-Глобус](https://www.bgoperator.ru/docs.shtml?action=list-api), [TEZ: заявки](https://www.tez-tour.com/ru/kemerovo/article.html?id=7015570).

Основные решения:

1. **Бесплатный широкий мультиоператорный поиск не подтверждён.** Бесплатный поиск одного поставщика и несколько раздельных виджетов доступны, но не обеспечивают единое сравнение основных выездных операторов.
2. **Собственный прямой агрегатор не рекомендуется как первый E5.** Главные расходы — договоры, нормализация, актуализация, поддержка адаптеров и качество данных. Отсутствие абонентской платы не делает владение дешёвым.
3. **Самый дешёвый найденный опубликованный отдельный широкий виджет — TourClient: 15 600 ₽/год**, но его handoff в Laravel и актуальное покрытие ещё надо доказать. Нельзя объявить его самым дешёвым *соответствующим всем требованиям* решением. [Калькулятор TourClient](https://www.tourclient.ru/calculator).
4. **Tourvisor Standard — наиболее обоснованный кандидат по совокупности стоимости и документированного экспорта.** Это предварительный выбор архитектуры, не окончательное коммерческое решение. Точные тарифы и сравнение приведены в §7–8.
5. **Если требуется немедленная собственная Booking после входа туриста, а модуль не поддержит надёжную передачу контекста, нужен API и собственный интерфейс.** Не следует имитировать этот сценарий разбором HTML или угадыванием пользователя по email.
6. Сохранить Tourist / Manager / Admin, правила назначения менеджера, чат, документы, уведомления и жизненный цикл. На первом этапе обращение не должно автоматически создавать финансовое обязательство или бронирование у оператора.

### 2.2. Существенные ограничения

**Цена пакета — особая точка риска.** В текущем контроллере при переданном локальном `tour_id` цена умножается на число взрослых и детей. Котировка внешнего пакетного тура может уже быть итогом на весь состав. Переиспользовать этот расчёт без изменения семантики нельзя: возникнет многократное завышение. Внешний quote должен иметь явное основание цены: за весь состав / за человека, валюту, доплаты и время проверки. Это архитектурное требование, не предложение патча. [Расчёт Booking](C:/wamp/www/Avilona_turfirma/app/Http/Controllers/Booking/BookingController.php:201).

`CoralTravelService` использует предполагаемые маршруты и значения по умолчанию, включая наличие мест и свойства перелёта; это нельзя представлять туристу как подтверждённые данные оператора. В Sletat-коде есть общий часовой кэш; из его наличия не следует, что разрешён часовой кэш живых котировок. Оба участка — материал для последующего ограниченного E5 review после выбора поставщика. [Coral](C:/wamp/www/Avilona_turfirma/app/Services/TourOperators/CoralTravelService.php), [Sletat](C:/wamp/www/Avilona_turfirma/app/Services/Sletat/SletatApiService.php).

Не требуется менять остальные публичные страницы и кабинеты. Область будущих работ: временный поиск, приём выбранного предложения, метаданные котировки, обработка внешних обращений, эксплуатация интеграции.

## 3. Russian package-tour data landscape

Для Avilona полезность данных надо оценивать по реальным запросам **из Санкт-Петербурга**, а не по числу логотипов поставщиков. Приоритет проверки: массовые пакетные направления; затем внутренние туры, проживание, экскурсионные и индивидуальные продукты. Москва — дополнительный вариант по выбору туриста, не незаметная замена отсутствующего вылета из Петербурга.

В исследованных источниках обнаружены разные технические и коммерческие слои:

| Слой | Что он действительно даёт | Чего из него не следует |
|---|---|---|
| Агентский сайт оператора | Поиск и работа менеджера с оператором | Разрешение автоматизировать его браузерные запросы или показывать данные потребителям |
| Официальный API оператора | Машинный поиск/расчёт/заявки в пределах конкретного договора | Доступ ко всем другим операторам на такой же платформе |
| XML/JSON feed | Машиночитаемые цены, справочники, иногда стопы | Гарантия актуальной цены и свободного места при выборе |
| Виджет оператора | Готовая витрина продукта этого оператора | Объединённая выдача нескольких операторов |
| Агрегатор | Объединение поставщиков, словарей и поиска | Одинаковая полнота пакетов, рейсов и бронирования у каждого поставщика |
| Affiliate/CPA | Вознаграждение за привлечённую продажу | Агентская бронь Avilona, владение заявкой, экспорт всех клиентских данных |
| CRM API | Клиенты, обращения, документы | Собственный источник туров или бесплатная лицензия поискового шлюза |
| Внутренние запросы сайта / scraping | Техническая возможность прочитать экран | Поддерживаемый контракт API и право на публикацию |

Различия видны на официальных примерах: отдельные API цен/заявок у [Библио-Глобуса](https://www.bgoperator.ru/docs.shtml?action=list-api), отдельные поисковые и контентные продукты [Tourvisor](https://tourvisor.ru/b2b/ddapi), расширения [Слетать.ру](https://sletat.ru/agency/xml/), собственные продукты [САМО](https://samo.plus/projects).

**Рабочая гипотеза для проверки покрытия**, а не статистика рынка: составить 20–30 запросов с вылетом СПб, ближайшими и дальними датами, 2 взрослыми и семьями с детьми разных возрастов. Для каждого сравнить оператора, пакет, итог после актуализации, перелёт и наличие. Отдельно проверить наземные туры. Только такой набор позволяет оценить полезность продукта для Avilona.

**Библио-Глобус.** Публичная ценовая инструкция описывает справочники, выгрузки пакетов и стопы; используются партнёрская авторизация и сессия. Есть требования к сессионным cookies и сжатию. Это официальный программный канал, а не рекомендация парсить сайт. В документах встречаются примеры 2026. Отдельный Tour API разделяет предварительный расчёт и создание заявки; он возвращает идентификаторы и суммы. Наличие старых примеров в Tour API требует проверки схемы с поддержкой. [Ценовая инструкция](https://export.bgoperator.ru/load-xml-prices.html), [создание заявки](https://www.bgoperator.ru/texts/api/tour-api.html).

**TEZ TOUR.** Документация описывает расчёт услуг/доплат, создание и получение заявки; контент имеет отдельный доступ. Но это не доказательство свободного действующего российского B2C-доступа. Во время повторного открытия общего URL вместо старой статьи появился официальный текст о восстановлении сервисов после инцидента ИБ; региональная страница документации ещё читалась. Дата инцидента на уведомлении не указана. Поэтому нельзя ни объявить оператора закрытым, ни считать шлюз проверенно работающим. Нужны актуальные endpoints, российское юрлицо, версия, тестовый ключ и подтверждение восстановления. [Уведомление](https://www.tez-tour.com/article.html?id=7015567), [региональная документация](https://www.tez-tour.com/ru/kemerovo/article.html?id=7015570).

**АЛЕАН.** Для будущего прямого направления следует выбирать между поисковым и полным интерфейсом по нужному продукту. Search-API не включает экскурсионные/активные туры, круизы и детские лагеря и не создаёт бронь; полный API покрывает более широкий цикл. Подробная сравнительная страница описывает SOAP, XML/JSON и дополнительные ограничения доступа. Способ выдачи логина/пароля и IP-доступ надо подтвердить непосредственно при подключении. [Сравнение интерфейсов](https://new.alean.ru/page/ta-api/?label=diff).

## 5. Can Avilona build direct multi-operator aggregation?

**Технически да; как ограниченная интеграция 1–3 поставщиков — реалистично. Как способ быстро получить широкий бесплатный поиск — практически не обосновано.** Сейчас есть один подтверждённо бесплатный договорный API и два серьёзных кандидата с неустановленными коммерческими/операционными условиями. Нельзя обещать Avilona 8–14 пригодных бесплатных подключений.

Концептуальный поток: браузер → Laravel → оркестрация нескольких разрешённых API → нормализация/краткоживущий кэш → результаты Avilona → перепроверка выбранного пакета → собственная заявка. Отдельные worker-процессы обслуживают справочники, допустимые выгрузки и восстановление внешних событий. Это не проектирование классов или схемы БД.

### 5.1. Реальная сложность владения

| Задача | Необходимое поведение | Почему это трудоёмко |
|---|---|---|
| Доступ | Отдельное разрешение и техническая учётная запись каждого поставщика | Договор агентства не всегда включает публикацию/автоматизацию; переговоры не параллелятся с готовностью к релизу |
| География | Свои устойчивые идентификаторы + соответствия поставщикам | Город, аэропорт, регион и курорт — разные сущности; «СПб» не всегда один код |
| Отели | Сохранять provider hotel ID, вести подтверждённые соответствия | Одно название может означать разные корпуса, ребрендинг, соседние объекты; нельзя сливать только по тексту |
| Номера | Исходное название сохранять; нормализовать только общие признаки | Standard/Promo/Economy, вид, корпус и bedding меняют продукт |
| Питание | Общие коды плюс оригинальное описание | UAI разных отелей не идентичен по услугам |
| Валюта | Разделять продажную валюту, валюту оператора и применённый курс | Курс оператора и срок его фиксации могут отличаться от справочного курса |
| Доплаты | Базовая цена, обязательные и выбранные услуги, итог | Неизвестный сбор не равен нулю; детский тариф не равен взрослому |
| Перелёты | Сегменты, аэропорты, местное время/часовой пояс, багаж, тариф | Несколько вариантов рейса могут давать разные итоговые цены одного отеля |
| Наличие | Различать «есть», «по запросу», «нет», «неизвестно» | Прайс не резервирует квоту; гостиница и рейс имеют отдельные ограничения |
| Дубли | Сравнивать пакет, даты, состав, номер, питание, рейсы, услуги, оператора | Дешёвый похожий пакет не обязательно взаимозаменяем |
| Fan-out | Независимые бюджеты времени, ограниченная параллельность, частичные результаты | Один медленный оператор не должен удерживать всю выдачу |
| Сбои | Повтор только безопасных чтений; временно отключать неисправного поставщика | Повтор создания брони может породить двойное обязательство |
| Изменения схем | Контроль контрактов ответов, предупреждения, сопровождение адаптеров | Каждый поставщик — самостоятельный жизненный цикл |

Это инженерная оценка на основе различий обнаруженных интерфейсов, а не обещания операторов.

### 5.2. Предлагаемые эксплуатационные правила

Числа ниже — **стартовые проектные гипотезы**, не разрешения поставщиков и не SLA:

- Первые доступные результаты показывать по мере поступления; общий бюджет интерактивного поиска ориентировочно 20–40 секунд с явным перечнем неответивших операторов. Настроить по PoC, не удерживать один веб-запрос до окончания всех источников.
- У каждого поставщика — собственные concurrency/rate-limit и бюджет квоты. Повторяющиеся одновременные запросы объединять только если это разрешено. Ограничения публичного Laravel API не заменяют ограничения внешнего договора.
- Справочники: ориентир обновления раз в сутки. Лицензированный контент: от суток до недели. Результаты поиска: 30–120 секунд или без повторного использования, если договор запрещает. Настоящий TTL устанавливать отдельно по API и типу ответа.
- Цену выбранного пакета актуализировать при переходе к заявке; перед бронированием у оператора — снова. После истечения срока показывать «требует перепроверки», а не продолжать считать цену действующей.
- При недоступной актуализации разрешать лишь обращение с неподтверждённой ценой и понятным уведомлением. Не показывать кнопку с обещанием подтверждённой покупки.
- Для feed-источника хранить время исходной выгрузки отдельно от времени загрузки в Avilona; ежедневный файл не становится real-time после чтения.
- Секреты, токены, сессионные cookies и агентские комиссии — только на сервере; ротация, минимальные полномочия, исключение из клиентского JS и журналов.
- Наблюдать задержки, долю ошибок, пустые ответы, расхождения search→recheck, расход квоты, потерянные handoff и возраст справочников. Корреляция по техническому request ID без паспортов/телефонов в метриках.
- Очередям нужны мониторинг, повтор с ограничениями, отдельная обработка окончательно неуспешных задач и восстановление после рестарта. Долгий импорт не должен блокировать импорт заявок.

### 5.3. Оценка труда

Оценки автора, не прайс подрядчика. Один человеко-день — 8 часов; включены анализ, интеграция, нормализация, UI, безопасность, QA и эксплуатационная документация. Договоры и ожидание доступа в сроки разработки не включены.

| Объём | Разработка | Календарный ориентир | Поддержка после запуска |
|---|---|---|---|
| Один прямой поисковый API без автоматического бронирования | 25–45 чел.-дн. | 5–9 недель одного разработчика с участием QA | 1–3 чел.-дн./мес. |
| Общий поиск 2–3 существенно разных операторов | 80–140 чел.-дн. | 4–7 месяцев одного основного разработчика | 4–10 чел.-дн./мес. |
| 8–12 операторов с приемлемой production-полнотой | 180–350 чел.-дн. | 9–18 месяцев одного основного разработчика; командой быстрее, но не линейно | 8–20 чел.-дн./мес., всплески при изменениях |

Автоматическое бронирование, изменения, отмены, платежи и документы у всех операторов заметно расширят эти границы. Уверенность оценок MEDIUM–LOW до доступа к частным спецификациям. Для небольшого агентства такой проект разумен только при самостоятельном коммерческом преимуществе, значительном объёме продаж или уже существующей технической команде — не ради экономии примерно одной недорогой лицензии модуля.

У Дельфина официально описаны адаптивность, отсутствие брендинга оператора и отправка обращения агентству по email. Это полезная бесплатная витрина, но email не равен структурированному callback в Laravel. Не рекомендуется строить основную интеграцию на распознавании писем, если нет согласованного стабильного формата. [Дельфин: условия](https://www.delfin-tour.ru/ta/export/).

**Не найдено подтверждённого предложения «бесплатный широкий поиск по основным операторам РФ + права на собственный UI + native lead API + без обязательного внешнего CRM/продавца».** Это результат публичного исследования, а не утверждение о невозможности индивидуальной договорённости Avilona.

### 7.2. Модуль, отображение и свежесть

Поставщик заявляет более 100 операторов для модуля; на API-странице — более 90. Эти цифры относятся к маркетинговым описаниям продуктов и не доказывают идентичный набор поставщиков. Попросить список операторов РФ по каждому тарифу, отдельно данные из СПб и ограничения динамических пакетов. [Описание модуля](https://tourvisor.ru/b2b/moduli-dlya-sajtov-turagentstv/poisk-turov), [API-продукты](https://tourvisor.ru/b2b/ddapi).

Официальные параметры встраивания позволяют задавать цвета, предустановленные направления/операторов/даты, способы показа результатов, мобильную адаптацию и представление цены. Есть `tv-customdata`, однако публичное описание не доказывает, что это поле возвращается в экспорте выбранной заявки. Документированного пригодного для Avilona callback **самого выбора тура** в изученных материалах не установлено. [Параметры разработчика](https://support.tourvisor.ru/rasshirennye-nastroiki/57-vstavka-koda-modulya-s-parametrami.html).

Вывод для существующего Blade-сайта: модуль можно разместить в текущей области поиска, сохранив навигацию и фирменную оболочку. Детальная свобода поведения внутри компонента ограничена поставщиком. Адаптивность заявлена, но мобильные сценарии Avilona, клавиатура, длинные названия, ошибки, back-navigation и авторизация требуют реального теста. Они не проверены этим исследованием.

Свежесть поисковой выдачи и окончательная цена — разные уровни. Рекламное обещание актуальности не заменяет проверку корзины оператора. Для публичного экрана следует различать «найдено», «актуализировано» и «подтверждено оператором». Точное время жизни результатов, поведение при истечении search/offer ID и перечень операторов с актуализацией — запросить.

SEO-вывод автора: загружаемый модуль нельзя считать гарантированно индексируемым каталогом Avilona. Существующие редакционные страницы направлений сохраняют ценность; бесконечные комбинации фильтров не следует превращать в индексируемые страницы. Собственный API-интерфейс даёт больше контроля, но не создаёт автоматически уникальный лицензированный контент.

### 7.3. Search API: подтверждённые возможности и границы

Публичная спецификация **1.2.4**: JSON, JWT; асинхронный старт → ID поиска → состояние/результаты → данные тура → авиарейсы и актуализация цены из корзины оператора. Есть справочники вылетов, направлений, отелей, операторов, валют, питание/размещение и параметры состава туристов. Отдельно оплачиваются описания отелей, номеров и горящие туры. Базовая выдача не равна полной фотобазе.

Включено 3000 тарифицируемых поисковых действий/сутки: старт, продолжение, актуализация. Чтение результатов не считается таким действием. Ограничения: 120 запросов/мин для справочников/описаний; 300 для остальных методов; ознакомительный режим — 300 запросов/сутки. В просмотренной Search-спецификации не найден контракт создания операторской брони. [Техническая документация](https://api.tourvisor.ru/search/docs).

Следовательно, собственный UI и собственная Laravel-заявка технически реалистичны. Полнота availability, отдельных сборов, трансфера и страховки должна проверяться по оператору и методу, а не предполагаться для каждого результата. Создание локального обращения не требует покупки внешней CRM; автоматическое бронирование у ТО — отдельный предмет лицензии/интеграции. Правила кэширования, хранение контента и SLA публичной спецификацией для проекта не закрыты.

### 7.4. Экспорт, webhook и собственная заявка

Документация экспорта описывает обычные и online-заявки, отдельные методы, API-ключ от поддержки, выборку по ID/`lastid`; форматы JSON/XML, для обычных также CSV. Webhook вызывает адрес клиента **GET-запросом с ID и типом**, после чего данные можно получить через API. Это не документированный POST полного заказа.

В обычном примере есть контакт, цена/валюта/топливный сбор, оператор, вылет, направление, отель, дата/ночи, размещение/питание/номер и ссылка оператора. Не показаны обязательные search ID, offer ID, hotel ID, структурированные детские возраста и подтверждённая корреляция с пользователем Avilona. Идентификатор экспортированной заявки не равен идентификатору тура. Online-формат богаче и включает чувствительные сведения. [Официальный экспорт](https://wiki.tourvisor.ru/).

**Архитектурный вывод:** импорт в Laravel возможен, но бесшовное создание Booking для уже вошедшего туриста зависит от доказательства корреляции. Есть два допустимых сценария:

1. Поставщик подтверждает поддерживаемую передачу непрозрачного контекста выбора; после проверки сервером Avilona турист входит/регистрируется, подтверждает параметры и создаётся его Booking.
2. Модуль передаёт только контактное обращение. Laravel принимает его во внутреннюю очередь обращений; менеджер связывает его с проверенным клиентом и создаёт Booking действующим способом. Это сохраняет основные действия менеджера в Avilona, но не даёт немедленного самостоятельного появления Booking в кабинете туриста.

Сценарий 2 требует небольшого собственного intake-процесса. Он **не существует сейчас** и не должен незаметно восстанавливать отменённый гостевой Booking flow. Если бизнес не допускает такой промежуточный шаг, модуль проходит PoC только по сценарию 1; иначе переходить к API.

Предлагаемые правила моста: webhook считать сигналом, данные забирать у известного поставщика с серверным ключом; повторные события объединять по provider + тип + ID; вести cursor отдельно по типам, повторять неуспешный импорт и периодически сверять пропуски. Непроверенную подпись/порядок/retry webhook не считать гарантированными. Никаких автоматических назначений прав по совпавшему email.

При модуле произвольный callback/webhook с полным tour context публично не подтверждён этим исследованием — запросить документ и образец. Наличие интеграций с известными CRM не доказывает произвольный webhook. Стилизация и настройки модуля описаны официально, но mobile/branding конкретной версии проверять в PoC. **Вывод:** включить в коммерческое сравнение модуля. API рассматривать только после письменной полной сметы с операторскими идентификаторами и актуализацией. Кэш, права на фото, лимиты сверх квоты, экспорт при прекращении и условия работы без CRM — UNKNOWN до договора.

### 8.2. TourClient / TourIndex

У TourClient есть отдельный модуль поиска и публичное предложение XML-шлюза для собственного сайта. XML описывает online-поиск, поиск по сохранённой базе и словари. В документации режим «БД» отличается от комбинированного; тип выставляет администрация сервиса, клиент не меняет его самостоятельно. Для Avilona нужен режим с текущими данными, а не только статистическая выгрузка. [Продукт XML](https://www.tourclient.ru/xml), [документация поиска](https://wiki.tourclient.ru/wiki/XML_экспорт/Поиск_туров).

Опубликованная цена **одного** поискового модуля: 5200 ₽/3 мес., 8400 ₽/6 мес., 15 600 ₽/год. В калькуляторе установка — 3000 ₽, рядом есть промоотображение бесплатной установки; применимость акции не подтверждена. Два модуля с mobile — 19 200 ₽/год; три — 22 800. Нельзя подменять цену одного поиска ценой комплекта или ценой витрины «горящих». [Калькулятор](https://www.tourclient.ru/calculator).

Маркетинговые страницы заявляют большой набор операторов, включая формулировку 160+; актуальный список реально работающих поисковых соединений и СПб-продукт надо запросить. У API **цена по запросу**; случайная сумма корзины на общей странице не является тарифом шлюза. Доступны варианты оформления, но полная свобода поведения не подтверждена. [Описание сервисов](https://www.tourclient.ru/service/view/1-promo-services/), [XML](https://www.tourclient.ru/xml).

Туристический лид, собственный Laravel, callbacks, финальная актуализация, booking API, rate limits, кэширование, лицензия контента и обязанности работать в стороннем кабинете — требуют конкретной документации. Поэтому TourClient — **ценовой конкурент для короткого PoC**, а не уже доказанная замена рекомендуемого моста. Профессиональные тарифы TourIndex по дням — отдельный продукт для агента, не доказательство включённого website/API. [TourIndex](https://tourindex.ru/info/plans).

### 8.3. САМО и API «Андромеда»

Нужно различать **операторское ПО САМО-тур**, агентскую CRM САМО-турагент и **агрегированный API Андромеды**. Общий backend операторов сам по себе не даёт одному агентству единый бесплатный доступ. [САМО-тур](https://samo.ru/tour/), [линейка продуктов](https://samo.plus/projects).

В актуальном официальном предложении Андромеды указаны **70+ операторов**, B2C/B2B, поиск, состав/изменение услуг пакета, реальное бронирование у оператора, статусы и документы. Это более близкий к полноценной операторской транзакционной интеграции кандидат, чем поисковый API без booking-методов. Публичное описание не заменяет матрицу поддержки каждого оператора. [API Андромеды](https://samo.plus/andromeda).

Публичный тариф: **B2C от 120 750 ₽/мес.; B2B от 262 500 ₽/мес., с НДС 5% по странице**. Предлагается запрос тестового доступа. Это исключает продукт из низкобюджетного первого E5 при обычном публичном тарифе. Специальный малый тариф не найден. [Прайс](https://samo.plus/price), [тест](https://samo.plus/test).

Собственный UI/Laravel возможен по назначению API; обязательность CRM, ключи операторов, пределы полномочий и контракт бронирования уточняются. Документация методов, ограничения, SLA, content-права и setup подлежат получению до оценки реализации. Старые публикации об SSAM-виджете и его цене нельзя выдавать за действующее предложение 2026. Найденное [демо SSAM](https://demo.samo.ru/ssam/) не подтверждает нынешнюю коммерческую доступность.

**Вывод:** серьёзная архитектурная альтернатива, если Avilona позднее потребуется автоматическое бронирование большого объёма и соответствующая экономика. Сейчас существенно дороже задачи.

## 9. Integration with Avilona Laravel application

### 9.1. Сохраняемая граница ответственности

**Поставщик отвечает за поиск и внешнюю котировку. Avilona — за идентичность клиента, своё обращение/Booking, менеджера, чат, документы и историю работы.** При реальном бронировании у ТО сохраняется его собственный номер и отдельный статус. Менеджеру всё равно может понадобиться операторский кабинет для подтверждения/документов, но это не причина вести вторую независимую CRM с дублем всей клиентской работы.

Концептуальная схема для API-варианта:

**Поиск Avilona → выбранное предложение → серверная актуализация → вход/регистрация и подтверждение клиентом → Booking Avilona → назначение менеджера → собственные чат/документы/уведомления → подтверждение у оператора → установленный жизненный цикл.**

Для модуля: **модуль → подтверждённый handoff → тот же поток**. Если передаётся только контактный лид: **модуль → внутреннее входящее обращение → проверка/связь с клиентом → Booking → тот же поток**. Эти варианты должны быть явно приняты как разные уровни UX.

### 9.2. Концептуальные сущности — не схема миграций

| Понятие | Назначение | Срок жизни и ограничения |
|---|---|---|
| Search context | Параметры поиска и внешний технический идентификатор | Краткоживущий; не превращать все результаты в каталог |
| Selected quote | Снимок конкретного выбранного пакета и результат проверки цены | Неизменяемая история версии предложения; актуальность хранить отдельно |
| Incoming inquiry | Только если модуль прислал неавторизованное обращение | Ограниченный доступ сотрудникам; без прав туриста до надёжной связи |
| Native Booking | Существующая заявка Avilona и её жизненный цикл | Основной рабочий объект кабинетов |
| External reservation reference | Номер/статус реально созданной позднее брони ТО | Не подменять им внутренний ID или права доступа |

Это модель ответственности. Не предписывается количество таблиц, названия полей БД, тип ORM-связи или реализация контроллеров.

### 9.3. Что сохранять локально при выборе

| Группа | Минимальный состав | Правило |
|---|---|---|
| Происхождение | Provider, channel/widget/API, operator ID/name, версия адаптера | Provider ≠ operator; оба значения нужны |
| Идентификаторы | Provider search ID, offer ID, hotel ID, внешний lead ID/type | Допускается отсутствие только с явной фиксацией и согласованным сценарием; не выдумывать ID |
| География | Departure city/airport, destination country/resort/city, исходные provider IDs | Сохранить нормализованное и исходное представления |
| Даты | Departure date/time, окончание, ночи, возможная разница ночей тура/отеля | Часовой пояс там, где есть время; без домысливания |
| Размещение | Отель, номер, питание, adults/children, возраста на поездку | Исходные названия плюс общие классификации |
| Пакет | Перелёты/багаж, трансфер, страховка, другие услуги, признак наличия | Отличать included / optional / unknown |
| Деньги | Quoted total, currency, basis whole-party/per-person, fuel/mandatory supplements, выбранные услуги | Decimal; исходная валюта сохраняется; неизвестное не равно 0 |
| Свежесть | Время quote, время получения, время revalidation, результат проверки, срок если дан | Состояния verified/stale/changed/unavailable/unknown — отдельно от Booking.status |
| История цены | Исходный и новый итог, причина изменения если передана, факт согласия туриста | Не переписывать молча первоначальное предложение |
| Ссылки | Поддерживаемый deep link, срок действия если известен | Не единственное место хранения существенных параметров |
| Бронь у ТО | Operator booking/reference ID, внешний статус, время последней сверки | Возникает позднее; созданный лид не является бронью |
| Правовая/техническая трасса | Источник согласия, версия уведомления, correlation ID | Минимально необходимые данные без лишних паспортов |
| Raw snapshot | Только нужный разрешённый фрагмент ответа | По договору, с ограничением срока и доступа; без ключей/сессионных cookies |

### 9.4. Важные правила совместимости

1. **User ID определяет Avilona.** Vendor email/телефон могут быть подсказкой сотруднику, но не доказательством владения аккаунтом. Переданный браузером user ID не принимать как полномочие.
2. **Webhook не вызывает обычную браузерную форму как доверенный пользователь.** Внешний приём — отдельная проверяемая граница; внутренний бизнес-процесс должен использовать существующие правила.
3. **Первоначальная котировка не равна согласованной стоимости Booking.** Выбор у поставщика не означает `confirmed`, а изменение цены не означает оплату.
4. **Повторная доставка — нормальный случай.** Создать одну заявку и одну цепочку уведомлений независимо от числа повторов и порядка событий.
5. **Существующие ограничения формы проверить по реальным продуктам:** дата строго после сегодня, ночи 1–30, состав до 10 взрослых/10 детей, возраст до 17. Не расширять их автоматически; либо фильтровать неподдерживаемый продукт, либо согласовать отдельный E5 slice.
6. **Не копировать внешний статус механически.** «Заявка принята», «на запросе», «оплачено поставщику» и «подтверждено» имеют разные значения. Только разрешённое действие сотрудника или надёжная согласованная автоматизация меняет внутренний статус.
7. **Права админа и менеджера сохраняются.** Наблюдение администратором не должно незаметно давать права участника защищённого диалога; проверяется существующая ролевая модель.
8. **Никаких паспортов на этапе обычного поиска.** Они нужны лишь на соответствующей стадии оформления и обрабатываются в защищённом контуре.

Основание существующих инвариантов: [BookingController](C:/wamp/www/Avilona_turfirma/app/Http/Controllers/Booking/BookingController.php), [BookingPolicy](C:/wamp/www/Avilona_turfirma/app/Policies/BookingPolicy.php), [маршруты auth](C:/wamp/www/Avilona_turfirma/routes/web.php:129). Остальное — предлагаемая концепция интеграции.

## 10. Architecture options A–F

Все оценки в этом разделе — инженерное сравнение автора при успешном договорном доступе. «Низкая стоимость» относится только к относительному сравнению, а не к обещанию нулевых расходов.

| Семейство | Стоимость / сроки | Возможности и качество | Native Avilona, риск и миграция |
|---|---|---|---|
| **A. Только прямые операторы** | Лицензии: 0 подтверждено лишь у АЛЕАН; прочее UNKNOWN. 80–140 чел.-дн. для 2–3, 180–350 для широкой сети | Полная свобода UI/бренда/mobile/SEO; покрытие зависит от договоров. Freshness/availability неоднородны | Native полностью возможен; высокая поддержка, договорные риски каждого источника. Независимость от агрегатора HIGH, зависимость от операторов остаётся. Частичные сбои переживает при правильной оркестрации |
| **B. Прямые API + агрегатор fallback** | Подписка агрегатора остаётся, плюс прямые адаптеры. Ориентир 70–120 чел.-дн. при одном прямом источнике и одном готовом агрегаторе | Хороший потенциальный охват; сложнее дубли, hotel matching и актуализация. Свобода HIGH | Native хороший; больше тестов и операционных связей. Имеет смысл после измерений продаж, не как стартовая экономия |
| **C. Агрегатор API + UI Avilona** | Search + content + разработка; 45–80 чел.-дн., 9–16 недель | Широкая выдача при доступе; UX/бренд/mobile/SEO под контролем Avilona; качество данных зависит от провайдера | Наиболее чистая связь с авторизованной Booking; средняя поддержка; централизованный риск vendor outage. Адаптер облегчает замену, но ID и контент требуют миграции |
| **D. Модуль + native handoff** | Низкая подписка; 15–30 чел.-дн., 3–6 недель после доступа | Быстрая широкая выдача; стилизация MEDIUM, полная UX-свобода LOW; mobile проверять, SEO ограничено | Лучший баланс для E5 при успешном PoC. Полная native-связь зависит от payload/identity; при contact-only нужен intake. Поиск заменить проще, чем весь бизнес-процесс |
| **E. Модуль + внешняя CRM** | Вставка 2–5 дней, плюс настройка/обучение/перенос процессов, возможная CRM-плата | Быстрый готовый путь, но чужие статусы/интерфейс и дополнительное место работы | Технически жизнеспособен, **не соответствует основному приоритету Avilona**. Самый сильный lock-in в работе менеджеров и истории; экспорт не гарантирован |
| **F. D сначала, C/точечные A позже** | Начальные затраты как D; дальнейшее расширение отдельными инвестициями | Ранний рабочий поиск, затем контроль UX/данных по реальной потребности | Рекомендуемая траектория. С первого дня Booking и история локальные, поставщик заменяем; цена будущего API/UI не исчезает |

Во всех семействах availability не является резервированием. Надёжность требует собственной формы обращения при сбое. Для A/B возможна частичная выдача оставшихся поставщиков; для C/D/E — полноценный поиск зависит от выбранного агрегатора. Для F резервная архитектура должна быть предусмотрена, но не нужно одновременно оплачивать и поддерживать второй агрегатор без доказанной необходимости.

### 12.3. Экономические пороги решения

Разница между опубликованными годовыми ценами одного TourClient-модуля и Tourvisor Standard — **3480 ₽/год**. Даже один дополнительный день нестандартного handoff способен перекрыть многолетнюю экономию при приведённой условной ставке. Поэтому дешёвый модуль полезен лишь при достаточном качестве и поддерживаемом импорте.

Поисковый API Слетать.ру с отельной базой по базовым строкам даёт 62 000 ₽/год, но это **не полная смета нужного E5**, пока не решены операторские данные и актуализация. Андромеда B2C по опубликованному месячному минимуму — от 1 449 000 ₽/год без собственной разработки. Эти вычисления показывают порядок затрат, а не обосновывают покупку. [Слетать.ру](https://sletat.ru/agency/extensions/), [Андромеда](https://samo.plus/price).

Если операторские подключения не дают заметно лучшего продукта/маржи, собственная широкая агрегация ради отмены небольшой абонплаты экономически не выглядит разумной. Окончательный расчёт нужен по реальным обращениям, конверсии и затратам менеджеров Avilona.

## 15. Recommended architecture

### 15.1. Primary

**Выбрать семейство D с траекторией F: website-модуль широкого поиска + поддерживаемый handoff в Avilona; первым проверять Tourvisor Standard.** Основание — документированный внешний экспорт, сравнительно низкая публичная цена модуля, возможность сохранить текущий сайт и независимый жизненный цикл. Это решение лучше соответствует масштабу агентства и срокам, чем создание сети операторских адаптеров.

Условие выбора принципиально: **не объявлять D полностью доказанным до PoC.** Принимать либо полноценную связь выбора с авторизованной Booking, либо явно согласованный собственный intake с конвертацией менеджером. Если нужен первый сценарий без компромисса и документация его не допускает, D отклоняется.

На первом релизе: поиск, карточка, полная доступная котировка, выбор, собственное обращение/Booking, назначение, существующие чат/документы/уведомления. Онлайн-оплату, автоматическое создание брони ТО, отмены и редактирование операторских броней не включать в минимальный scope: они не нужны для заявочного процесса пользователя и существенно расширяют ответственность.

### 15.2. Fallback

**Технический fallback при несостоятельном widget handoff — семейство C: Search API с интерфейсом Avilona.** Tourvisor API наиболее прозрачен по публичной современной спецификации среди рассмотренных подходящих по цене кандидатов. Получить отдельную смету с контентом и подтвердить права перед выбором.

**Коммерческий конкурент** — модуль Слетать.ру; **ценовой конкурент** — TourClient. Их можно предпочесть, если они предоставят документированный native handoff, достаточный СПб-продукт и лучший полный бюджет. Не выбирать поставщика по номинальной разнице цены до проверки этих условий. При жёстком нулевом бюджете — АЛЕАН/Дельфин как честно ограниченный поиск, с отдельным согласованием того, что широкий E5 остаётся незакрытым.

### 15.3. Migration path

1. С первого дня собственные Booking, история цены и границы данных отделены от UI поставщика.
2. Измерить реальные запросы, конверсию и ручные проблемы менеджеров. Переход к API должен решать наблюдаемую проблему, а не просто давать более красивую архитектуру.
3. Заменить модуль собственным API-UI, сохранив local workflow и историю. Переносить только разрешённый контент; старые provider IDs не выдавать за IDs нового поставщика.
4. При подтверждённой выгоде добавить один прямой источник: АЛЕАН для внутреннего продукта или BG для конкретной востребованной группы пакетов. Только после договора и измеримого выигрыша.
5. Расширять прямую сеть по окупаемости. Не ставить «избавиться от любого агрегатора» обязательным условием завершения E5.

### 15.4. Прямые ответы на 11 бизнес-вопросов

| Вопрос | Ответ |
|---|---|
| 1. Реалистичен ли широкий бесплатный поиск? | **В публично подтверждённой форме — нет.** Возможно индивидуальное соглашение, но оно не получено |
| 2. Что бесплатно доступно частично? | АЛЕАН API по договору и отдельные операторские виджеты. Это один/несколько ограниченных каталогов; долю рынка или массовых выездных продаж оценить без данных нельзя |
| 3. Разумно ли строить свой прямой мультиагрегатор? | **Не как первый E5 небольшого/среднего агентства.** Один целевой адаптер позднее может быть разумен |
| 4. Почему? | Неподтверждённые права и доступ плюс дорогие нормализация, актуализация, поддержка и обработка сбоев; экономия лицензии мала относительно владения |
| 5. Tourvisor лучший? | **Самый обоснованный первый кандидат по исследованным публичным данным**, но не безусловный победитель. Sletat/TourClient могут выиграть после quote/PoC; Андромеда сильнее в транзакциях, но намного дороже |
| 6. Widget или API? | **Модуль, если handoff проходит критерии; API, если необходим полный собственный UX/авторизованная связь и модуль её не обеспечивает** |
| 7. Можно ли сохранить Laravel/cabinets? | **Да.** Это основной архитектурный принцип; потребуется слой приёма котировки/обращения, а не замена кабинетов |
| 8. Самая дешёвая credible production architecture? | Для ограниченного ассортимента — бесплатный операторский модуль. Для широкого поиска — low-cost module + native handoff; окончательно самый дешёвый end-to-end пока не доказан. Lowest public sticker: TourClient; наиболее доказанный bridge-кандидат: Tourvisor |
| 9. Самая быстрая credible architecture? | Готовый модуль + проверенный native handoff, без платежей и autobooking. Bare embed с заявкой только во внешней CRM не закрывает приоритет |
| 10. Лучшая долгосрочная независимость? | Практически — собственные UI/процесс/quote-модель с заменяемым API-поставщиком и точечными direct-источниками. Максимальная независимость от агрегатора — полный direct, но дорогая |
| 11. Что E5 должен делать первым? | Закрыть коммерческие/технические неизвестные и провести короткий handoff/coverage PoC; затем минимальный D или C, а не начинать большую сеть интеграций |

### Обязательные проверки PoC

PoC ориентировочно 3–5 человеко-дней внутри общей оценки, после получения доступа. Это не бесплатный «кусочек production» и не закупка лицензии заранее.

- Поиск из СПб по согласованным 20–30 комбинациям; проверить основные операторы Avilona и корректную пустую/частичную выдачу. Процент достаточного покрытия согласовать до теста — нет оснований выдумывать его сейчас.
- Выбрать реальные по структуре пакетные варианты: 2 взрослых; семья с ребёнком; разные рейсы/багаж; обязательный сбор; наземный продукт.
- Сверить исходный результат, актуализацию и переданное обращение: отель, оператор, даты, состав, цена и все доступные IDs не теряются.
- Пройти оба identity-сценария: уже вошедший турист и посетитель без аккаунта. Нельзя выдавать контактный лид за Booking кабинета, если связь не доказана.
- Повторить webhook, нарушить порядок, отключить импорт, затем восстановить; получить одну запись и одно логическое уведомление.
- Проверить просроченный offer, изменение цены, отсутствие мест и timeout. Турист видит понятный результат, менеджер — контекст, а не «успешно забронировано».
- Проверить узкий экран, клавиатуру, возврат назад, отсутствие горизонтального скролла и совместимость со стилями сайта.
- Зафиксировать расход запросов на один пользовательский путь. Сверить с тарифом, включая revalidation и повторы.

**Go для D:** доказан поддерживаемый handoff и согласованный identity-путь, достаточное покрытие, полный для выбранного scope payload, native работа менеджера и понятные права. **No-go для D:** только email/ручное копирование при требовании автоматизации; нет стабильного контекста; обязательная внешняя CRM; запрет native обработки. Тогда проверить C, а не строить обход чужого интерфейса.

Для реализации позже нужны focused-тесты интеграционных границ и существующих правил авторизации/Booking, затем принятые в проекте проверки. Тесты этого исследовательского документа не заменяют будущую техническую приёмку; canonical MySQL не использовать для PHPUnit вопреки ограничениям проекта.

### Stop conditions перед большой реализацией

1. Нет письменного права на B2C/совместную выдачу и нужный контент — не начинать массовое подключение/копирование.
2. Нет test key или воспроизводимого payload — не фиксировать окончательную схему данных и трудоёмкость.
3. Неясна цена полного пакета услуг/допов — не выбирать по стартовой цифре и не оплачивать длинный период.
4. Не доказана связь с владельцем Booking — не обещать автоматическое появление заявки в его кабинете.
5. Поиск не даёт нужного СПб-продукта — не считать E5 успешным из-за красивого demo.
6. Нет способа revalidation — не обещать окончательную цену/наличие; согласовать более ограниченный заявочный сценарий или сменить поставщика.
7. API требует оборота/договора, которого у Avilona нет, — это внешний коммерческий блокер, а не задача программирования.
8. Частные docs, SLA, export/ownership и operator coverage не предоставлены — сохранить UNKNOWN, не заполнять вымышленными характеристиками.

Публичное исследование достаточно для выбора **приоритетного направления и PoC**, но не для безусловного утверждения поставщика, цены договора и даты production-запуска.
